# ライフプランシミュレーター：本体同期の実機検証ゲート

確認日：2026-10-22 JST。対象：Draft PR #28の開発ブランチ。本人データは対象外。

## 現在確認したこと
- 本人PCとiPhone Safariが検証用 `pair-check` に個別接続し、同じ **架空暗号文** をPC→iPhone→PCで受け渡し、最後に削除・不存在を表示した。証拠は利用者の診断結果であり、独立した管理ログではない。
- アプリ本体の同期実装は未公開。模擬Firebaseを使った実アプリChrome/WebKit別保存領域の検証では、初回送信・確認後取込・再起動・変更受信・競合停止を確認できる。架空の比較案・実績・年次点検・未知フィールドを含む完全状態の照合を追加した。
- 計算エンジン、個人の採用値、公開main、実環境のFirestore Rules、Authユーザー、課金は変更しない。

## 実クラウドで本体同期を始められない理由
**現行のアプリ本体の保存先と、検証用Firestore Rulesの許可先が異なる。**
- Draftの `sync-firebase.mjs` は認証UIDごとに `owners/{uid}/snapshots/current` を読書きする。
- 現行sandbox Rulesテンプレートは `sandbox/{testUid}/snapshots/trial` だけを許し、その他を拒否する。
- 既存の`pair-check`プレビューは架空データの専用ページであり、通常アプリの保存データを読み込まない。このページの成功を、本体同期の実機合格と読み替えない。

したがって、現行Rulesと検証ページのままで本体を使用しても、正規のデータ送受信は成功しない。Rulesを黙って緩めたり、本番 `lifeplan-private-sync` へ架空データを書き込んだりしない。

## 次に進むために必要な設計・承認
1. **ブラウザ保存の隔離**：PCの通常アプリとiPhone Safari/PWAの各保存領域を決して使い回さない。新しい、期間限定の、検証専用Hostingプレビューで架空アプリだけを起動する。既存`pair-check`を上書きせず、URLごとに分離する。
2. **sandbox試験用Rules変更案**：本人用Firebase Rulesは触らない。検証プロジェクトに限り、検証用UIDだけが `owners/{testUid}/snapshots/current` の限定作成・更新・読取りをできるか検討する。終了後の削除手順が必要だが、アプリ本体には削除操作がないので、明示的に承認された特定文書のクリーンアップを別経路で用意し、所有者・形式・世代・暗号文を再照合してから削除する。既存trialルール・文書を維持する。
3. **実機受入れ**：PCの架空設定・比較案・実績・年次点検を新プレビューへ入力し、iPhone側の架空既存値を別領域でバックアップ。送信元の明示選択、受信前差分表示、取込、再起動後一致、未保存入力保護、オフライン復帰、競合停止、復元動作を確認する。
4. **本番公開と本人データは別**：CI合格、実機合格、公開差分、戻し方を確認した後に本番公開の承認を行う。本人データ初回同期はさらに別の明示承認が必要。

## 現段階の結論
- 架空データでのプログラム検証を自動で進めることは可能。
- 新規Hostingプレビュー公開・Firestoreルール変更・検証文書の上書きや削除は**まだ承認範囲外**。実行前に対象・差分・影響・復旧方法を具体化し、必要な承認を求める。
- 本人が現時点で操作する必要はない。テスト件数だけで端末実機や本人用データの安全性を保証しない。
